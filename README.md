# 運動でモンスターを倒すダイエットゲーム（仮）

運動を記録すると、その分だけモンスターに攻撃できる。運動の成果を「ダメージ」という目に見える形で返すことで、続かないダイエットを続けられるようにするゲームです。

---

## 1. 背景と課題

ダイエット・運動習慣が続かない最大の原因のひとつは「成果が見えず、実感がわかないこと」です。体重はすぐには変わらず、努力してもフィードバックが遅いため、多くの人が数日で挫折します。

このアプリは「運動 → 攻撃 → モンスターのHPが減る」という因果を即座に見せることで、努力の成果をその場で実感できるようにし、運動を続ける動機を作ることを狙います。

## 2. 誰の・どんな課題を解決するか

- **想定ユーザー**：運動を習慣にしたいが、成果が見えず続かない人（自分たち、家族など）
- **中心にある課題**：
  - 運動しても効果が実感できず、モチベーションが続かない
  - そもそも「何をすればいいか分からない・考えるのが面倒」で、始める前に止まってしまう
- **解決の方針**：
  - 運動の成果を即座に「ダメージ」として可視化し、モンスター討伐という短期目標で達成感を積み重ねる
  - 運動メニューを提案し、「今日は何をやろう」という迷いをなくして行動につなげる

## 3. ゲームの仕組み

1. ユーザーが運動を記録する（例：腕立て10回、ランニング2km）
2. 運動内容に応じて攻撃力が決まり、モンスターにダメージを与える
3. モンスターのHPを削り切ると討伐成功、次のモンスターが出現する
4. 倒すごとに強い敵が出る／レベルが上がる、といった成長要素で継続を促す
5. 「ボスは数日かけて倒す」など中期目標を置き、三日坊主を防ぐ

## 4. 運動提案機能

「何をすればいいか分からない」という離脱の原因に対応するため、運動メニューを提案する機能を用意します。これも段階的に育てます。

### 第1段階：リストからランダム提案
- あらかじめ運動メニューのリストを用意しておく（例：腕立て10回、その場ジャンプ30秒、スクワット15回）
- ボタンを押すと、その中から1つをランダムに提案する
- AIも外部サービスも不要で、データを用意するだけなので最小版に足しやすい

### 第2段階：条件に合わせた提案
- 「きつめ／軽め」「室内／外」「時間5分／15分」などの条件を選べるようにする
- 選んだ条件に合ったメニューを出し分ける
- 条件分岐で作れるので、要件を整理してロジックに落とす練習になる（上流工程の実践）

### 将来の拡張候補：AIによる提案
- 気分・使える時間・レベルなどを入力すると、その場でメニューを生成する
- 「AIを組み込んだアプリ」として技術的な見栄えは出るが、最小版より後の拡張として検討する

## 5. 設計上の判断（なぜそうしたか）

チーム開発・上流工程の練習も兼ねて、「なぜその選択をしたか」を明文化します。

### 運動量は自己申告制にする
- 歩数計やセンサー連携が理想だが、まずは「この仕組みが継続に効くか」を検証したい
- そのため最小版では入力手段をシンプルにし、自己申告で割り切る
- 将来的に歩数計連動へ拡張できる余地は残す（MVP → 段階的拡張の判断）

### シングルプレイ＋複数セーブデータに対応する
- 一台の端末を家族で共有して使う想定があるため、プレイヤーごとに別々の進捗を持てるようにする
- セーブスロット（新規作成／続きから）で複数プレイヤーを切り替えられる
- 各セーブデータが持つ情報：プレイヤー名・レベル・攻撃力・討伐数・運動記録の履歴

### データ保存はまずブラウザ内（localStorage）で行う
- サーバーやデータベースがなくても複数セーブは実現できる
- 環境構築でつまずかず、まず動くものを作ることを優先する
- 「別端末からもログインしたい」等の要求が出た段階で、初めてサーバー・DB・ログイン機能を検討する（必要になってから作る判断）

## 6. 最小版（MVP）の範囲

まず「ダイエット×ゲーム」の核が動く、最小限の形を作ります。

- 運動を1種類だけ記録できる
- 記録するとモンスターに固定ダメージが入る
- HPバーが減り、0になったら「討伐！」と表示される
- セーブスロットを選んでプレイヤーごとにデータを保存できる
- ボタンを押すと運動メニューを1つランダムで提案する

この最小版が動いたら、運動の種類を増やす → モンスターを増やす → レベル制を足す、の順で育てていきます。

## 8. 技術構成

- フロントエンド：HTML / CSS / JavaScript
- データ保存：ブラウザ内保存（localStorage）※将来的にDB・サーバーへ拡張の余地あり
- バージョン管理：GitHub

AIの支援を受けてコードを書く前提だが、要件・設計・データ構造・運動量の換算といった「何を・なぜ作るか」の判断は自分たちで行い、その記録を残す。

## 9. 進め方（ロードマップ）

1. **第1段階**：MVP（運動1種→固定ダメージ→討伐、複数セーブ）を完成させる
2. **第2段階**：運動の種類を増やし、種類ごとにダメージを変える
3. **第3段階**：モンスター・レベル・実績などの成長要素を追加
4. **第4段階（拡張）**：歩数計連動やサーバー・ログインを検討
